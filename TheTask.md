# ТЗ: прототип генерации документов для практики студентов

Учебный проект. Цель прототипа — пройти сквозной сценарий от загрузки списков студентов и компаний до  распределения студентов и генерации направлений и приказа. 

## 1. Назначение и границы прототипа

Пользователь загружает список студентов и список компаний. Приложение формирует документы Word (.docx): пакет направлений для указанной группы и один приказ по всем загруженным студентам.

## 2. Входные данные

| Файл | Формат и поля | Использование |
|---|---|---|
| Список студентов | Excel (.xlsx), ФИО и группа | Импорт студентов; группа используется для фильтрации направлений |
| Список компаний | Текстовый файл (.txt) в кодировке Windows-1251; одна компания на строку, строка содержит название и город, название компании от адреса компании разделяется запятой | Импорт компаний и распределение студентов |

При невозможности прочитать файл или при отсутствии обязательных данных API возвращает понятную ошибку.

Компании в БД соответствуют организациям (модель `Organization`).

## 3. Распределение студентов

Два варианта: 1| Назначить конкретную компанию всей группе. 2| Назначить отдельно каждому студенту
Также отдельный хендл для редактирования компании у студента. 


## 4. Выходные документы

Документы формируются по имеющимся DOCX-шаблонам в каталоге `templates/`.

| Документ | Область генерации | Логика |
|---|---|---|
| **Направления** | Одна группа, заданная в запросе | Один DOCX-файл. Для каждого студента выбранной группы формируется отдельный бланк направления; между бланками вставляется разрыв страницы. В каждом бланке указывается компания, назначенная студенту. |
| **Приказ** | Все загруженные студенты | Один DOCX-файл с пронумерованным списком всех студентов и назначенных им компаний. Порядок строк соответствует порядку студентов при загрузке. |

Пользователь указывает группу только при генерации направлений. Приказ включает всех студентов, независимо от группы.

Сведения, которых нет во входных файлах (например, тип и даты практики, руководитель), в документах оставляются пустыми. Прототип не должен подставлять вымышленные значения или требовать отдельную загрузку этих данных.

Если группа не найдена или нет студентов, то raise error

## 5. API и взаимодействие

FastAPI Swagger UI (`/docs`) используется как интерфейс загрузки файлов и вызова операций; отдельный frontend не требуется.

Предусмотреть операции:

```text
POST /import/students              multipart/form-data: список студентов (.xlsx)
POST /import/organizations         multipart/form-data: список компаний (.txt)
POST /practice/create?group= (Назначить преподавателя для группы, указать тип практики)
POST /practice/company?(group= | student=) (Распределить компании по студентам (3 варианта распределения)) 
GET  /documents/directions?group=  скачать направления для указанной группы (.docx)
GET  /documents/order              скачать приказ по всем загруженным студентам (.docx)
```

Сценарий пользователя:

1. Загрузить список студентов.
2. Загрузить список компаний.
3. Создать практику, назначить преподавателя. 
4. Запросить направления, передав группу; скачать единый DOCX с разрывами страниц между направлениями.
5. Запросить приказ; скачать DOCX со всеми загруженными студентами.

Распределение выполняется приложением автоматически по кругу и используется при формировании обоих документов.



## 7. Технические ограничения

- **FastAPI** — HTTP API и Swagger (`/docs`).
- **SQLite** и **SQLAlchemy** — хранение загруженных студентов и компаний.
- **pandas + openpyxl** — чтение Excel-файла студентов.
- Стандартные средства Python — чтение текстового файла Windows-1251.
- **docxtpl** — заполнение DOCX-шаблонов; для направлений используется цикл по студентам с разрывом страницы.
- Без отдельного frontend, авторизации, ролей, Celery/Redis и фоновой генерации.

Поток обработки: `Router → Service → Repository → DB`; генерация документов: `Router → Service → выборка/распределение → docxtpl → скачиваемый DOCX`.
