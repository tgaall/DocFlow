# ТЗ: прототип генерации документов для практики студентов

Учебный проект. Цель прототипа — пройти сквозной сценарий от загрузки списков студентов и компаний до автоматического распределения студентов и генерации направлений и приказа. Сводный отчёт и оценки в прототип не входят.

## 1. Назначение и границы прототипа

Пользователь загружает список студентов и список компаний. Приложение распределяет студентов по компаниям равномерно по кругу и формирует документы Word (.docx): пакет направлений для указанной группы и один приказ по всем загруженным студентам.

Распределение автоматическое и детерминированное: студенты и компании обрабатываются в порядке строк соответствующих файлов. Ручное изменение назначений в прототипе не предусмотрено.

## 2. Входные данные

| Файл | Формат и поля | Использование |
|---|---|---|
| Список студентов | Excel (.xlsx), ФИО и группа | Импорт студентов; группа используется для фильтрации направлений |
| Список компаний | Текстовый файл (.txt) в кодировке Windows-1251; одна компания на строку, строка содержит название и город | Импорт компаний и распределение студентов |

Импорт сохраняет порядок строк, поскольку он определяет порядок циклического распределения и строк приказа. Пустые строки не создают записи. При невозможности прочитать файл или при отсутствии обязательных данных API возвращает понятную ошибку.

Компании в БД соответствуют организациям (модель `Organization`). Если входная строка содержит название и город, приложение сохраняет строку как отображаемое название компании; отдельное выделение города в прототипе не требуется.

## 3. Распределение студентов

Студенты назначаются компаниям по кругу в порядке строк исходных списков. Например, при списке компаний `A, B, C` студенты получают назначения `A, B, C, A, B, C...`.

Результат распределения должен быть детерминированным: студенты и компании выбираются из БД по возрастанию `id` (порядок первого импорта), поэтому при неизменных списках назначения совпадают. Сводная сущность практики, руководитель и отдельный ручной CRUD распределений для этого прототипа не требуются.

Если список студентов или компаний пуст, распределение и генерация документов не выполняются; API возвращает ошибку с объяснением причины.

## 4. Выходные документы

Документы формируются по имеющимся DOCX-шаблонам в каталоге `templates/`.

| Документ | Область генерации | Логика |
|---|---|---|
| **Направления** | Одна группа, заданная в запросе | Один DOCX-файл. Для каждого студента выбранной группы формируется отдельный бланк направления; между бланками вставляется разрыв страницы. В каждом бланке указывается компания, назначенная студенту. |
| **Приказ** | Все загруженные студенты | Один DOCX-файл с пронумерованным списком всех студентов и назначенных им компаний. Порядок строк соответствует порядку студентов при загрузке. |

Пользователь указывает группу только при генерации направлений. Приказ включает всех студентов, независимо от группы.

Сведения, которых нет во входных файлах (например, тип и даты практики, руководитель), в документах оставляются пустыми. Прототип не должен подставлять вымышленные значения или требовать отдельную загрузку этих данных.

Если группа не найдена или нет студентов, то raise error

## 5. API и взаимодействие

FastAPI Swagger UI (`/docs`) используется как интерфейс загрузки файлов и вызова операций; отдельный frontend не требуется.

Предусмотреть операции:

```text
POST /import/students              multipart/form-data: список студентов (.xlsx)
POST /import/organizations         multipart/form-data: список компаний (.txt)
GET  /documents/directions?group=  скачать направления для указанной группы (.docx)
GET  /documents/order              скачать приказ по всем загруженным студентам (.docx)
```

Сценарий пользователя:

1. Загрузить список студентов.
2. Загрузить список компаний.
3. Запросить направления, передав группу; скачать единый DOCX с разрывами страниц между направлениями.
4. Запросить приказ; скачать DOCX со всеми загруженными студентами.

Распределение выполняется приложением автоматически по кругу и используется при формировании обоих документов.

## 6. Минимальная модель данных

```text
Student(id, full_name, group)
Organization(id, name)
```

Распределение рассчитывается при генерации документов по студентам и компаниям, выбранным в порядке возрастания `id`; отдельная таблица `Assignment` для прототипа не нужна.

## 7. Технические ограничения

- **FastAPI** — HTTP API и Swagger (`/docs`).
- **SQLite** и **SQLAlchemy** — хранение загруженных студентов и компаний.
- **pandas + openpyxl** — чтение Excel-файла студентов.
- Стандартные средства Python — чтение текстового файла Windows-1251.
- **docxtpl** — заполнение DOCX-шаблонов; для направлений используется цикл по студентам с разрывом страницы.
- Без отдельного frontend, авторизации, ролей, Celery/Redis и фоновой генерации.

Поток обработки: `Router → Service → Repository → DB`; генерация документов: `Router → Service → выборка/распределение → docxtpl → скачиваемый DOCX`.

## 8. Вне рамок прототипа

- Сводный отчёт.
- Импорт ведомостей, выставление оценок и статус защиты.
- Списки руководителей и практик, учёт сроков и типа практики.
- Ручное распределение, редактирование назначений и рекомендации по выбору компании.
- Определение дополнительных атрибутов компании (категория, оплата, зарубежная/российская и т. п.), если их нет во входном файле.
- Отдельные сущности групп и сложное управление дублями/историей импортов.
- Авторизация, роли, отдельный frontend, очереди задач и асинхронная генерация.
